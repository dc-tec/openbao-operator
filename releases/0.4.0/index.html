OpenBao Operator 0.4.0

Security-boundary hardening, explicit delegation for high-impact controls, and safer self-initialization.

Updated 9 August 2026 · 1 min read

On this page
  • Highlights
  • Before upgrading

Published 4 July 2026.

0.4.0 focuses on security-boundary hardening, explicit delegation for high-impact controls, safer self-initialization for auto-unseal clusters, and broader lifecycle testing.

Highlights

  • require explicit Kubernetes authority for network publication, custom helper images, trust roots, cloud identity references, restore delegation, and other dangerous controls
  • reject more ambiguous or unsafe Hardened cluster shapes
  • protect operator-managed resources with provenance and admission guardrails
  • add initial recovery-key bootstrap for self-initializing auto-unseal clusters
  • clean one-shot bootstrap configuration after initialization succeeds
  • expand property and model-based tests for lifecycle-critical behavior

Before upgrading

  1. Review existing cluster and restore resources against the new delegated authorization and Hardened validation rules.
  2. Grant only the delegated roles each human or GitOps identity needs.
  3. Apply the 0.4.0 CRDs before upgrading the controller or chart.
  4. Validate admission, reconciliation, backup, restore, and human authentication in staging.
upgrade

Upgrade the Helm release

helm upgrade openbao-operator \
  oci://ghcr.io/dc-tec/charts/openbao-operator \
  --version 0.4.0 \
  --namespace openbao-operator-system \
  --reuse-values
!

Treat this as a security-hardening release

Stage the CRD and admission-policy update, validate representative cluster specs, and audit the difference between ordinary cluster authors and platform administrators before production rollout.

Open the published GitHub release for artifacts, signatures, provenance, and the complete generated change list.
